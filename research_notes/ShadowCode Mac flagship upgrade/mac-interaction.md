# Mac interaction standards and ShadowCode flagship shell

Research date: November 11, 2026. Scope: Apple Silicon Mac priority; workspace navigation, split views, toolbar hierarchy, keyboard/focus, typography, accessibility, and reduced motion. This is an implementation brief based on source inspection and primary documentation, not an implemented redesign or a native accessibility certification.

Audited repository: `/Users/shadowfetch/Projects/ShadowCode`; branch `cursor/apple-silicon-t3-ux-610c`; initial clean HEAD `82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0`. Source links below are immutable links to that commit. Other contributors subsequently modified shell files and added `PanelResizeHandle.tsx`, `flagship.css`, and browser-test/report artifacts; those edits were preserved. A later read-only snapshot of these uncommitted files is distinguished explicitly below from the immutable baseline. Reconcile these recommendations with the working tree before implementation. The only file written by this researcher is this note.

External evidence is restricted to official Apple HIG and primary product documentation from VS Code, Cursor, and Zed. Apple pages were read through their official `.md` alternatives where HTML required JavaScript. These are live documents accessed on the research date; search-engine crawl dates are not treated as publication or release dates. Recommendations below are explicitly design inferences, not claims that Apple prescribes a particular AI coding layout.

## 1. What workspace and toolbar structure should replace the remaining chat-shell limitations?

### Takeaway

Prioritize the implementation now in progress: direct Files/Terminal/Preview toolbar access, persisted and clamped split sizing, Mac hints, and richer empty-state cards. Keep the current behavior APIs and chat-plus-drawer hierarchy; the highest-impact next work is making visibility, command state, resizing, and keyboard focus agree.

### Cited Findings

- **Preserve the 2.4.0 baseline.** The changelog records native arm64 preference under Rosetta, Metal resource checks, architecture diagnostics, one-screen project entry, inline provider connection/local download, and working/done/approval thread states. These are documented existing changes, not new recommendations or independently rerun runtime qualifications. [ShadowCode changelog, lines 5–11](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/CHANGELOG.md#L5-L11)
- **Apple navigation model.** Sidebars organize top-level destinations, normally with at most two hierarchy levels, disclosure groups, and a discoverable hide/show action. Apple allows automatic collapse when a window becomes narrow. [Apple HIG: Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)
- **Apple split-view model.** Adjacent panes can express hierarchy or support a central work surface; persistent selection maintains orientation. macOS supports horizontal and vertical arrangements with draggable dividers. [Apple HIG: Split views](https://developer.apple.com/design/human-interface-guidelines/split-views)
- **Current navigation already has useful semantics.** Projects group task buttons, disclosures expose `aria-expanded`, the active task has `aria-current`, and task status uses icons/text and accessible labels. Pins and keyboard context-menu access exist. Avoid replacing this with an unlabeled icon-only activity rail. [Sidebar.tsx](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/Sidebar.tsx#L118-L240), [project groups](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/Sidebar.tsx#L294-L341)
- **Verified structural constraint.** `DrawerTab` includes Changes, Git, Terminal, Preview, Files, Tasks, and Tools; one `tab` condition selects content. `App` mounts one drawer next to the conversation stage. Consequently, Files and Terminal cannot remain visible together through this shell. This is a concurrency-of-views limitation, not evidence of lost data. [Drawer.tsx, lines 45–69](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/Drawer.tsx#L45-L69), [conditional contents](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/Drawer.tsx#L201-L250), [App shell](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/App.tsx#L658-L810)
- **Fixed geometry, no shell resizing contract.** Rail/drawer defaults are 254/420 CSS pixels; breakpoint overrides are 220/370 at widths up to 1150 and 270/480 above 1600. Grid tracks consume these fixed values. The inspected shell has no interactive divider or persisted pane width. [tokens.css](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/tokens.css#L35-L43), [workspace.css grid](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/workspace.css#L34-L48), [breakpoints](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/workspace.css#L975-L1026)
- **Concrete navigation defect from source.** At ≤1150 CSS pixels with a drawer open, CSS hides `.sidebar`, but React's `sidebar` value remains true. `TopBar` renders Show Sidebar only when that value is false. Toggling the preference cannot reveal the sidebar while the CSS condition remains in force; closing the drawer restores it. This needs a browser/native reproduction, but the contradictory state/render rules are explicit. [workspace.css, lines 981–991](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/workspace.css#L981-L991), [TopBar.tsx, lines 38–49](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/shell/TopBar.tsx#L38-L49)
- **Panel state preservation already exists.** App-owned drawer memory retains active files, buffers, terminal selection, commit/PR drafts, and preview configuration per workspace during the application session; editor recovery has additional persistence logic. Terminal shells live in the engine and mounting replays their output. Do not claim that changing drawer tabs currently destroys terminal sessions or unsaved buffers. [useDrawerMemory.ts](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/hooks/useDrawerMemory.ts#L25-L85), [TerminalView.tsx](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/TerminalView.tsx#L1-L3)
- **Competitor precedent.** VS Code documents simultaneous primary/secondary sidebars, persistent view placement, visible layout controls, and reset commands. Cursor documents an Agent layout toggle and remappable shortcuts. Zed documents left/right/bottom dock sizing and configurable bottom-dock arrangement. These show concrete interaction patterns, not proof of superior usability or market demand. [VS Code custom layout](https://code.visualstudio.com/docs/configure/custom-layout#_secondary-side-bar), [Cursor shortcuts](https://cursor.com/docs/reference/keyboard-shortcuts), [Zed settings](https://zed.dev/docs/reference/all-settings#resize-all-panels-in-dock)
- **Toolbar standard and current gap.** Apple places navigation at the leading edge, important/inspector actions at the trailing edge, recommends logical grouping, and requires macOS toolbar actions to be available in the menu bar. Baseline `TopBar` emphasizes Comparisons, Changes, and search; Files/Terminal/Preview have no equivalent top-level layout controls. [Apple HIG: Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars), [TopBar.tsx](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/shell/TopBar.tsx#L50-L98)

### Inferences

**Scope update from the implementation owner.** The active work is direct toolbar access, Mac shortcut hints, a persisted/clamped keyboard-and-pointer split handle, and richer empty-state cards, while preserving behavior APIs. That scope supersedes the earlier exploratory multi-region redesign. Simultaneous Files/Terminal remains a baseline limitation, but a new docking architecture or layout-preset system is explicitly deferred, not a prerequisite for this upgrade.

**Read-only review of the early working tree (mutable snapshot, November 11).** These observations are about newly written implementation, not HEAD:

**P0 effective visibility without API churn.** Preserve the existing `panel` enum, callbacks, drawer memory, and terminal lifecycle. Distinguish the user's sidebar preference from effective presentation at the current width. A stable sidebar control must remain available when layout collapses it. At narrow widths its action must actually reveal navigation, for example through a deliberate temporary navigation presentation or by switching away from the tool panel. Do not merely toggle a boolean that CSS continues to suppress. When a panel closes, restore focus to its invoking toolbar button or previous focus destination.

**P0 resizer acceptance contract.** Verify pointer deltas at native webview zoom and CSS fallback zoom, legal `aria-valuemin <= aria-valuenow <= aria-valuemax`, and matching spoken/effective widths after viewport changes. The inspected implementation retains `preferred` separately from the computed maximum; preserve that useful distinction. Test restoring a wide preference into a narrow window and expanding again. Keep resize operations free of editor/terminal remounts. The current 8px handle needs a clearly visible focus indicator and discoverable keyboard instructions; do not assume a narrow divider must look like a 28px-wide button. Consider persisting on gesture completion or a short debounce instead of synchronous storage writes for every pointer event. These are targeted implementation recommendations, not demands for a new framework.

**P1 toolbar hierarchy.** Keep three groups: project/task identity; Files/Terminal/Preview tools; Changes and secondary commands. Selected panel, focused control, and active task need distinct appearances. Keep the text labels at ordinary widths and stable accessible names when compact rules remove them. Comparisons can stay secondary; hiding its text should not hide its command or meaning. Keep destructive decisions and permission changes in their existing explicit workflows. Use the existing platform hint helper consistently, but separately correct actual shortcut collisions.

**Deferred exploration only.** A bottom terminal and primary-width code/review surface could eventually address the mutually exclusive drawer. Do not implement that architecture in this pass without a concrete workflow need. The present direct-access/resizable split is a substantive upgrade if focus, accessibility, and saved state are completed coherently.

### Gaps

No interactive app was launched, so the narrow-window defect is source-derived, not a recorded user-visible reproduction. No claim is made about exact native title-bar/traffic-light spacing. Repository configuration targets macOS 12 or later, so any newer material treatment needs a compatibility path. [macOS bundle configuration](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/src-tauri/tauri.macos.conf.json#L1-L11)

Proposed acceptance checks: at 1380×920, keep the conversation and chosen file/terminal/preview panel usable while resizing; at 1024-wide and 520-wide content areas, every hidden region remains explicitly recoverable. Resize and switch panels with unsaved edits, a running terminal, preview navigation, and a PR draft; verify preservation and absence of accidental process creation. Repeat at increased zoom. These are future implementation checks, not tests passed during this study.

## 2. What keyboard, focus, and native command behavior needs to change?

### Takeaway

Build a shared command and focus model before adding more chrome. Existing dialog and tab behavior is worth keeping; the remaining problems are inconsistent command semantics, Mac shortcut collisions, and missing region-level navigation.

### Cited Findings

- **Platform shortcuts.** Apple says to respect standard shortcuts; its table assigns Command-M to minimize, Command-grave to switching app windows, Control-Tab to the next control group, and Control-F6 to the next panel. A web frontend should not assume Command and Control are interchangeable on Mac. [Apple HIG: Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards)
- **Actual shortcut claims.** `shortcutFor` uses `ctrlKey || metaKey`, maps M to the model picker, grave/Dead to Terminal, and Control-Tab to recent conversation. Alt-Up/Down navigation also runs without excluding editable fields. Native menu delivery may intercept some combinations before JavaScript receives them; the code establishes collision risk, not which handler wins in the installed app. [useShortcuts.ts, lines 47–103](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/hooks/useShortcuts.ts#L47-L103)
- **Changes shortcut differs from its toolbar action.** The shortcut executes `setPanel(p => p ? null : "changes")`, so an open Files or Terminal panel is closed instead of switched to Changes. The toolbar only closes an already-open Changes panel. A shared action should eliminate this discrepancy. [App.tsx shortcut](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/App.tsx#L470-L485), [toolbar callback](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/App.tsx#L693-L700)
- **Mac hint migration is partial.** Sidebar uses the existing platform-aware `shortcutHint`; TopBar still embeds Ctrl+B, Ctrl+Shift+B, and Ctrl+K. The helper already recognizes Apple client platforms, including remote usage. [shortcuts.ts](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/lib/shortcuts.ts#L1-L11), [TopBar.tsx](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/shell/TopBar.tsx#L38-L95)
- **Preserve working focus protections.** `Dialog` captures its opener, contains Tab/focus, handles Escape, and restores focus when the opener remains connected. Drawer tabs use a single selected Tab stop, arrow/Home/End movement, and manual activation so merely traversing tabs does not start terminal/preview work. The global shortcut listener respects `defaultPrevented`, modal ownership, and terminal input. [Dialog.tsx](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/Dialog.tsx#L17-L88), [Drawer.tsx](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/Drawer.tsx#L139-L190), [useShortcuts.ts](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/hooks/useShortcuts.ts#L57-L78)
- **Region focus and close restoration are incomplete at shell level.** Shortcut actions include composer focus but no next/previous-region action. Drawer close is a state update without a generic opener-restoration mechanism; terminal mounting explicitly focuses the terminal. This should not be described as a total lack of focus management. [shortcut actions](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/hooks/useShortcuts.ts#L14-L37), [drawer close](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/App.tsx#L799-L805), [terminal focus](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/TerminalView.tsx#L126)
- **Native integration inspection.** Window configuration titles the main window “ShadowCode.” Searches of `src-tauri/src` and `ui/src` found no app-specific menu builder/event wiring or main-window title updates; inspected setup builds the configured window. This does not establish that Tauri supplies no default menus. [window configuration](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/src-tauri/tauri.conf.json#L22-L35), [native setup](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/src-tauri/src/main.rs#L447-L542)
- **Focus standard and competitor pattern.** Apple distinguishes focus from selection, discourages unsolicited focus movement, and recommends visible text-field focus. VS Code documents F6/Shift-F6 region navigation, one Tab stop per toolbar/tablist with arrow navigation, an editor Tab-escape mode, and an Accessible View for chat and terminal content. [Apple HIG: Focus and selection](https://developer.apple.com/design/human-interface-guidelines/focus-and-selection), [VS Code accessibility](https://code.visualstudio.com/docs/configure/accessibility/accessibility)

### Inferences

**P0 command parity using current APIs.** First reuse a shared handler for toolbar and keyboard Changes actions and centralize shortcut metadata; a broad command framework is not necessary to fix the verified discrepancy. As the native menu grows, define each command once with an ID, label, platform binding, enabled state, checked/expanded state where appropriate, and handler. Reuse that definition in toolbar, palette, help, native menu, and keyboard routing. Start with project opening, task creation, sidebar/panel visibility, Changes, terminal, composer focus, settings, zoom, and stop. Specify whether each command means “show and focus,” “toggle visibility,” or “select”; use the same behavior from every entry point.

Use Command as the primary Mac modifier, Control on other platforms, and explicit Control bindings only when intended. Preserve minimize/window cycling and editor/terminal text behavior. Candidate terminal and model-picker replacements must be tested against macOS, VoiceOver, keyboard layouts, and editor bindings before committing a default. Do not resolve a collision by silently documenting a different key from the actual handler. IME composition and Alt/Option text navigation deserve explicit guards.

**P0 focus ownership within the current hierarchy.** Give navigator, conversation, workspace drawer, and toolbar named focus destinations; give the split handle an explicit route into keyboard navigation. Store the last focused control within each region; user-invoked commands restore it or focus a predictable fallback. Closing a region restores its invoking control when possible. Async output, layout measurement, and task completion must not move focus. Hidden regions must leave the focus order. Keep native control navigation and provide menu/palette commands for next/previous region; F6 can be an additional editor convention, not a replacement for macOS shortcuts.

A wide-layout drawer/panel is nonmodal. For compact layouts choose deliberately between a full primary-surface switch and an actual modal sheet with background inertness and focus containment; a fixed overlay must not ambiguously cover still-focusable content. Preserve existing manual activation in panel tabs, particularly for terminal and preview side effects.

**P1 native menu and identity.** Wire the shared commands into appropriate native menus and retain standard app/window actions. Update native window identity to project and current task/document; retain the in-content heading. This is more consequential than drawing imitation traffic lights. Verify actual native menus before replacing anything supplied by the runtime.

### Gaps

Native shortcut arbitration, Full Keyboard Access, VoiceOver reading order, editor Tab escape, and multi-window cycling were not exercised. Source inspection cannot establish screen-reader usability. The research therefore treats these as implementation and qualification requirements.

Proposed acceptance scenario: using only the keyboard, select a project/task, open a file, move into the terminal, return to the editor, review changes, open and close settings, and restore prior focus. Confirm that typing/editing shortcuts remain local, Command-M still minimizes, layout restoration does not steal focus, and toolbar/menu/palette commands agree. Include a non-US keyboard and IME composition. Verify region navigation with VoiceOver enabled and disabled.

## 3. What visual, typography, accessibility, and motion system should guide implementation?

### Takeaway

Retain the system font and theme foundation, but promote important work controls above caption-sized chrome and add semantic accessibility preferences. Use quiet opaque work surfaces and clear selection/focus states; expensive visual effects are not evidence of Apple Silicon quality.

### Cited Findings

- **Typography baseline.** Apple lists macOS body text at 13 pt with 16 pt line height, callout at 12/15, subheadline at 11/14, and footnote/captions at 10/13. It recommends readable weights, a clear hierarchy, and preserving that hierarchy when text size changes. Therefore 10–12-sized metadata is not automatically a HIG violation. [Apple HIG: Typography](https://developer.apple.com/design/human-interface-guidelines/typography#macOS-built-in-text-styles)
- **Existing strengths and density mismatch.** Global body text is 13px/1.5 with an Apple-system-first font stack. However task rows, project headings, and the task title are 12px; top actions, drawer tabs, and status text are 11px. Important navigation and commands are concentrated at secondary/caption-like sizes. These are CSS pixels, not measurements of rendered native points. [index.css](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/index.css#L9-L17), [tokens.css](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/tokens.css#L35-L43), [navigation](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/workspace.css#L158-L205), [toolbar](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/workspace.css#L264-L310), [drawer tabs](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/workspace.css#L901-L927)
- **Scaling exists.** Appearance controls already support persisted zoom and preview. Native webview zoom is used with a CSS fallback, and terminal measurement compensates for CSS zoom. Recommend independent reading-size controls as an extension, not “add zoom.” Zed documents separate UI, editor, and agent typography settings, establishing a primary competitor precedent. [useAppearance.ts](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/hooks/useAppearance.ts), [useZoom.ts](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/hooks/useZoom.ts#L45-L64), [Zed typography settings](https://zed.dev/docs/reference/all-settings#agent-ui-font-size)
- **Accessibility requirements.** Apple lists 28×28 pt default and 20×20 pt minimum macOS controls; recommends sufficient contrast in both themes, increased-contrast support, non-color status cues, labels, and testing with assistive technologies. These point sizes are not a blanket 44px desktop requirement. [Apple HIG: Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- **Contrast adaptation is not implemented in the inspected shell.** Tokens supply fixed light/dark palettes and state a 4.5:1 text-contrast intention; `useAppearance` exposes theme and zoom. Searches found no `prefers-contrast`, `forced-colors`, reduced-transparency handling, or native display-accessibility bridge in the inspected UI/native source. The token comment is not a measurement of every rendered component. [tokens.css](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/tokens.css#L1-L71), [useAppearance.ts](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/hooks/useAppearance.ts)
- **Focus and status already have treatment.** There is a global focus outline and a sidebar-search focus underline. Task states have non-color indicators. Only the status label is a polite atomic live region, while the conversation log disables live reading, avoiding token-stream announcements. Preserve these distinctions. [focus CSS](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/workspace.css#L11-L14), [search underline](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/workspace.css#L105-L117), [StatusBar.tsx](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/shell/StatusBar.tsx#L42-L57), [ChatView.tsx](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/shell/ChatView.tsx#L154-L156)
- **Reduced motion already exists, but does not cover every behavior.** A global media query shortens CSS animations/transitions and disables smooth CSS scrolling; a JavaScript helper chooses instant scrolling. Yet terminal configuration sets `cursorBlink: true` with no motion-preference subscription, and submit hover/active transforms remain declared even when transition durations collapse. Static transforms may become instantaneous rather than disappearing. [motion.ts](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/lib/motion.ts), [reduced-motion CSS](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/workspace.css#L1084-L1092), [terminal options](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/TerminalView.tsx#L59-L71), [submit transforms](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/workspace.css#L1404-L1413)
- **Motion standard.** Apple recommends purposeful, optional, brief feedback, avoiding unnecessary motion on frequent interactions and not blocking people while animations complete. This supports removing decorative pulses and scaling from a continuously used coding surface. [Apple HIG: Motion](https://developer.apple.com/design/human-interface-guidelines/motion)

### Inferences

**P1 visual specification — calm, legible work surfaces.** Proposed starting tokens, subject to actual Mac rendering and user testing:

| Role | Proposed default | Purpose |
|---|---|---|
| Project/task rows and main commands | 13px system font, medium for active items; 30–32px rows | Make navigation readable without expanding every badge |
| Current task/document heading | 14–15px semibold | Distinguish identity from toolbar actions |
| Conversation prose | 14–15px with 1.5–1.6 line height; approximately 70–85 characters per line | Support sustained reading |
| Code and terminal | Independently adjustable, starting around 13–14px | Improve code legibility without forcing all chrome to grow |
