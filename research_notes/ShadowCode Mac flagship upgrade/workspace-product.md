# Modern coding workspace product structure

## 1. What should be discoverable, and how should projects lead into conversations?

### Takeaway

ShadowCode 2.4.0 already contains substantial workspace functionality. The flagship opportunity is to give that functionality a coherent, persistent navigation model: project → conversation → changes/checks, with Files and Terminal available without first discovering the Changes drawer. Treat this as a structural evolution of the existing product, with usability hypotheses to validate, rather than a missing-feature inventory.

### Inferences

**Proposed product model:** Project is the working context; Conversation is the persistent discussion; Run is an execution attempt; Review is inspection of a named change scope. The current user-facing word “task” spans session creation/history and execution results. Clearer labels can reduce that ambiguity without renaming backend entities.

**Proposed structural layout:** retain the project/conversation sidebar; use a persistent project header with explicit active location; give the main area stable Conversation, Files and Review destinations; provide a visible Run/checks control and an execution/output surface with Terminal and Preview. Keep Comparisons available through More/palette and its existing view, promoting it when relevant. Keep Goals, Automations and Worktrees in secondary navigation. This is a proposed hierarchy, not a requirement to introduce five simultaneous panes or reproduce VS Code.

**Proposed end-to-end path:** open project → start or resume a conversation in that project → see selected agent/model and permission mode → send → inspect progress and any approval → inspect task changes → run/review checks → optionally stage/commit. Each transition should have an explicit destination and return path. A conversation switch should preserve an unsent draft; a layout switch should preserve both the draft and current file work.

### Gaps

- Source inspection establishes render paths, labels and state wiring, not actual discoverability or layout quality. No screenshots, live interaction or measured task completion times were collected.
- No user-frequency data establishes whether Comparisons deserves its current prominence. Test this before permanently demoting a distinctive workflow.
- Full relaunch persistence, long project lists, duplicate project names and active worktree labeling need runtime qualification. Existing source should not be read as proof of those experiences.

## 2. How should review and execution remain visible and trustworthy?

### Takeaway

The most important improvement is a persistent task outcome surface that separates agent progress, file changes, human review and verification. ShadowCode already has unusually explicit check receipts and freshness handling; the new shell should expose and preserve them instead of inventing a generic green “Done” state.

### Cited Findings

**Official behavior:**

- Zed exposes changed-file counts beside the message editor and opens an aggregate review with hunk or whole-change controls. — [Zed review](https://zed.dev/docs/ai/agent-panel#reviewing-changes)
- VS Code distinguishes pending edits from Git operations: Keep clears pending-review state and does not stage or commit. Its documentation warns that tool-specific change lists may omit terminal/script changes. In the Agents window, a reviewed-file marker clears if the file changes again; review behavior varies by harness. — [VS Code review and revert](https://code.visualstudio.com/docs/agents/run/review-code-edits)
- JetBrains provides a named Run output tab for each application configuration, supports pinning output across reruns, and exposes execution controls in that tool window. — [IntelliJ Run tool window](https://www.jetbrains.com/help/idea/run-tool-window.html)
- Claude Code's VS Code documentation separates permission mode from review, supplies conversation history, and exposes background tasks through an agent map with output and stop controls. Its walkthrough is dismissible and can be reopened. Some controls have explicit extension-version requirements. — [Claude Code in VS Code](https://code.claude.com/docs/en/vs-code)

**ShadowCode's existing foundations and exact remaining gaps:**

1. **Review exists at two scopes with different entry points.** `reviewChanges(path, taskId)` opens full-width task review when a task ID is supplied; without one it opens the working-tree Changes drawer. Header Changes directly toggles that drawer and uses `git.count`. Task review has “This task” and “Git” tabs and a Back to conversation button. The scope split is intentional; the discoverability concern is that the shared wording does not explain it before entry. — [App routing](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/App.tsx#L340), [header wiring](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/App.tsx#L680), [ReviewView](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/ReviewView.tsx#L109)
2. **Keep is a local review marker.** `useReview.ts` explicitly documents that Keep changes nothing on disk. File markers store paths under a task key; hunk markers store path/hunk IDs. In the inspected hook, `keepFile` does not bind the marker to file content or a revision. “Undo all” skips kept files. This establishes a review-freshness design limitation, not a demonstrated destructive runtime failure. — [Review marker implementation](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/hooks/useReview.ts#L22), [marking and undo selection](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/hooks/useReview.ts#L119)
3. **Run a check already bypasses model generation.** The explicit command dialog creates a new command task, preserves historical evidence, shows its project, and retains normal approvals. The hook guards wrong session/workspace, duplicate submission and delayed results. Its wired UI action reaches `TaskSummary` through transcript row actions; the inspected header and palette do not offer a Run a check action. Thus a completed transcript summary is the current discoverable entry point, not a persistent workspace control. — [RunCheck](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/RunCheck.tsx#L58), [useRunCheck](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/hooks/useRunCheck.ts#L19), [App action](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/App.tsx#L563), [summary entry](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/TaskSummary.tsx#L326), [palette](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/shell/palette.ts#L28)
4. **Verification already distinguishes provenance and freshness.** TaskSummary differentiates vendor-reported verification, no check, recorded execution, and unconfirmed claims; receipt details include directory, attempt, source and output. It states that visible evidence is periodically reassessed while original receipts remain in history. Tests explicitly exercise immediate clearing of green state, project scoping and pending reads. Tests were inspected, not run. — [TaskSummary evidence UI](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/TaskSummary.tsx#L381), [freshness tests](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/TaskSummary.freshness.test.tsx#L172)
5. **Execution information is distributed.** StatusBar reports Working/Paused/Reconnecting/Ready and branch. Detailed activity is inside ChatView, while background Processes is under Tools and explicit check results are in task summaries. Review replaces the visible conversation; Stage keeps its milestone announcer outside that hidden view. Therefore it is inaccurate to say all progress or accessibility announcements disappear in review, but there is no equivalent persistent visual run/check dashboard in these shell components. — [StatusBar](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/shell/StatusBar.tsx#L42), [ChatView](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/shell/ChatView.tsx#L228), [Stage](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/shell/Stage.tsx#L324), [Tools](https://github.com/ShadowfetchStudio/ShadowCode/blob/82c60ee6a8bb8174c617d92aae0c8d5b14bc82a0/ui/src/components/ToolsTab.tsx#L13)

### Inferences

**Proposed persistent summary:** show separate fields for execution status, changed-file scope/count, review progress, and check status. Example: “Agent finished · This task: 3 files · 1 needs review · Checks: stale.” Each field opens its evidence. Do not derive check success from agent completion, backend connectivity, or the model's prose.

**Proposed review semantics:** retain both task and workspace changes, label the selected scope explicitly, and show Git actions as a separate stage. “Mark reviewed” more closely describes the current Keep operation, but this is not a safe text-only rename: kept files also affect Undo all. Preserve that behavior explicitly or redesign and test the selection semantics together. Track reviewed state against a content/diff revision; changes invalidate the marker. Unattributed workspace edits must remain visible without asserting that the selected task created them.

**Proposed execution hierarchy:** one Runs/checks entry can summarize command checks and offer links to terminal/process output without merging their lifecycles. A dev server being alive is not a passing check; a stopped agent need not imply a stopped server. Retain task/project/session identities in all actions.

### Gaps

- No live experiment verified stale Keep markers after an external file edit. The source-level representation warrants a focused regression test before making stronger claims.
- Backend API support for revision-bound review markers and a consolidated run history was not audited. If identifiers are insufficient, record that as a prerequisite; do not fabricate UI evidence.
- Source inspection does not establish how reliably every provider reports changed files or commands. Keep unknown and provider-reported states explicit.

## 3. What should be implemented first, and how will success be measured?

### Takeaway

Prioritize three connected deliverables: explicit scoped review, persistent Runs/checks, and a project-scoped workspace shell. Follow with guided first-task onboarding and secondary navigation cleanup. All numbers below are proposed acceptance targets, not observed performance or competitor statistics.

#### Minimum flagship implementation boundary

A substantive first delivery should complete R1–R4 as one coherent path: select project → create conversation → run work → inspect explicitly scoped changes → execute/inspect checks → return to the same draft. Merely adding a header strip, recoloring cards, or adding a welcome checklist would not meet this proposed boundary. R5–R6 can follow once the core flow is stable.

Sequence the work as follows:

1. Define a small navigation contract: active workspace, conversation, main view, review scope/task, selected run and optional output surface. Keep derived run/check status derived from existing evidence rather than storing a second success flag. Define return behavior and unknown/error states before rendering new surfaces.
2. Promote existing review/check components and define their scope labels. Add revision-aware review tracking if the evidence API supports it; otherwise make that missing contract explicit before shipping review-progress badges.
3. Refactor shell destinations around those components, preserving `useDrawerMemory` and conversation draft ownership. Add project-scoped creation with stale-response protection. Avoid duplicating the file editor, terminal or review mutation handlers.
4. Exercise the full scenario matrix below; then add the optional learning checklist and consolidate secondary destinations. Resolve terminology with user testing before broad internal renames.

#### Validation plan and measurement definitions

**Baseline first.** Run the same tasks on untouched 82c60ee and on the candidate build using matching project fixtures and comparable participants. Record completion, time-to-first-correct-action, wrong turns, assistance and lost-state incidents. Do not infer that reducing click count necessarily improves completion time. One “navigation action” means one click/key activation of an already visible control; opening a menu counts, typing and backend execution time are recorded separately.

**Human study.** Proposed pilot: 10 developers unfamiliar with ShadowCode, split between agent-heavy and conventional-editor experience. Counterbalance version order and use equivalent task variants to reduce learning effects. Report raw counts and median timings; this sample is formative, not evidence of population-wide statistical significance. Target at least 8/10 unassisted completions per core navigation task and a 25% reduction in median time to find a task diff and its check evidence versus the measured baseline. If the baseline is already faster, revise the design rather than claiming success from aesthetics.
